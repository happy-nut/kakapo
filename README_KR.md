# Kakapo

**AI가 실제로 무엇을 바꿨는지 읽는 데스크톱 diff 리더. 작업 중인 저장소에서 터미널로 실행합니다.**

*[English README](README.md)*

코딩 에이전트는 빠릅니다. 그 결과물을 읽는 쪽이 느리죠. Kakapo는 그 반쪽을 위해 만들어졌습니다 — 진짜 diff, 진짜 language server 탐색, 코드 옆에 남는 리뷰 코멘트.

## 왜 Kakapo인가

**근거는 채팅 로그가 아니라 diff입니다.** 에이전트의 "완료 ✅"는 주장일 뿐입니다. Kakapo는 실제 Git diff를 IntelliJ 스타일 side-by-side로 열고, 접힌 문맥을 펼치고, `F7`로 hunk를 넘기고, 파일별 *Viewed* 상태를 남깁니다. 보고된 내용이 아니라 들어온 변경을 봅니다.

**코멘트는 코드 옆에 남습니다.** 라인에서 `?`를 눌러 질문이나 변경 요청을 남깁니다 — 한 라인에 코멘트는 하나입니다. 이미 코멘트가 있는 라인에서 다시 `?`를 누르면 새로 쌓이는 대신 그 코멘트가 열립니다. `F8`로 열린 스레드를 끝까지 훑고, `⌘⇧/`로 열린 코멘트 전체를 한 문서로 모아 복사합니다 — 앞에 붙는 지시문 없이 코멘트만. 에이전트가 있는 곳에 붙여넣으면 됩니다. 복사는 인계이므로, 넘긴 코멘트는 리뷰에서 비워집니다(`⌘Z`로 되돌릴 수 있습니다) — 다음 인계가 이미 보낸 카드를 다시 싣지 않습니다. 스레드 자체는 평문 파일이라, 그 경로를 받은 에이전트는 답변을 질문한 카드 위로 되돌려 붙일 수 있습니다.

**설치 없이 IDE 수준으로 읽습니다.** definition·references·implementation·workspace symbol이 실제 language server로 diff 위에서 동작하고, Semantic Peek이 리뷰를 벗어나지 않고 그 자리에서 답을 보여줍니다. 프로젝트 검색은 번들된 ripgrep으로 돌아갑니다. 9개 언어의 분석기와 실행 환경이 앱 안에 들어 있어 `PATH`도, 별도 설치도, 에디터 플러그인도 필요 없습니다.

**추적되는 프로젝트 파일에는 아무것도 쓰지 않습니다.** 리뷰 스레드는 `.git/` 안에 있습니다 — git은 자기 디렉터리를 추적하지 않으니 `git status`는 깨끗하고, cwd에 갇힌 코딩 에이전트도 그 파일에 닿을 수 있습니다. 나머지 상태는 워크스페이스 절대 경로별로 OS 애플리케이션 데이터 디렉터리에 격리됩니다. 전부 평문 JSONL/Markdown/JSON, 완전 로컬, 계정도 텔레메트리도 없고 MIT입니다.

## 리뷰 루프

1. 에이전트는 사용자의 터미널에서 작업합니다.
2. 그 저장소에서 `kakapo`를 실행해 diff를 읽습니다 — `F7`로 hunk 이동, `Space`로 파일 확인 표시.
3. 라인에서 `?`로 질문하거나 변경을 요청합니다.
4. `⌘⇧/`로 열린 코멘트 전체를 한 문서로 모으고, 복사해서 에이전트가 있는 곳에 붙여넣습니다. 넘긴 코멘트는 그 자리에서 비워집니다.

## 설치

### macOS (Apple Silicon)

```bash
brew install --cask happy-nut/tap/kakapo
```

앱과 함께 `kakapo` 명령어까지 설치되므로, 저장소에서 바로 `kakapo .`을 쓸 수 있습니다. 서명되지 않은
빌드인데 cask가 quarantine 플래그를 떼어 줍니다 — [Releases](https://github.com/happy-nut/kakapo/releases)에서
`.dmg`를 직접 받으면 그 처리가 없으니 첫 실행은 우클릭 → **열기**가 필요합니다.

`brew upgrade --cask kakapo`로 이후 릴리스를 따라갑니다.

### 소스에서

Node.js 22.14 이상이 필요합니다.

```bash
git clone https://github.com/happy-nut/kakapo.git
cd kakapo
npm install
npm run lsp:install
npm link
kakapo install-app   # 선택: Applications에 Kakapo 아이콘 추가
```

`npm`이 설치하는 건 명령어이지 애플리케이션이 아니라서, kakapo는 터미널에만 있고 Spotlight·Launchpad에는
뜨지 않습니다. `kakapo install-app`이 Applications에 아이콘을 만들어 줍니다 — 방금 설치한 그 CLI를 그대로
실행하는 런처라 따로 관리할 사본이 생기지 않고, `kakapo uninstall-app`으로 지웁니다.

## 실행

Git 저장소나 모노레포 내부 패키지 폴더에서 실행합니다.

```bash
kakapo
kakapo /path/to/repository/package     # 또는 아무 폴더나
kakapo path/to/file.ts                 # 그 파일이 있는 폴더를 열고 파일에 바로 안착
```

Git은 선택입니다. 저장소가 아닌 폴더는 diff가 빈 소스 트리로 열립니다 — 커밋할 생각이 없던 파일을 읽을
때가 그렇습니다. `~/.claude` 밑의 설계 메모, 임시 폴더, 풀어 놓은 tarball 같은 것들.

Kakapo는 한 번만 실행됩니다. 같은 저장소나 worktree에서 다시 실행하면 이미 그것을 리뷰 중인 창으로 이동하고, 다른 저장소는 자기 창을 엽니다. 하위 폴더는 Git top-level로 정규화되므로 같은 checkout이 두 번 열리지 않고, 서로 다른 worktree는 각각 독립된 창으로 남습니다.

### 비교 대상 고르기

툴바의 pill이 지금 무엇을 비교 중인지 말해 주고, 누르면 하루 종일 오가게 되는 두 상태가 열립니다.

| 키 | |
| --- | --- |
| `⌥A` | 이 브랜치의 모든 변경 — 고른 브랜치와의 merge-base 기준 |
| `⌥U` | 아직 커밋하지 않은 것만 |
| `⌥C` | 그 브랜치 고르기 — 목록에서 검색하거나 저장소 기본값 그대로 |

"모든 변경사항"은 브랜치 tip이 아니라 **merge-base**를 씁니다. 그냥 `git diff main`을 하면, 그사이 움직인 `main`의 남의 커밋이 내가 지운 것처럼 보이기 때문입니다.

아무 플래그 없이 열면 kakapo가 알아서 고릅니다 — push하지 않은 커밋이 있으면 upstream의 merge-base, 아니면 `HEAD`. 실행할 때 직접 지정할 수도 있습니다.

```bash
kakapo --base main          # working tree vs main (AI 피처 브랜치 전체 리뷰)
kakapo --base v0.2.0        # 특정 태그와 비교
kakapo --base 9f3c1a2       # 특정 커밋과 비교
kakapo --staged             # 인덱스 vs HEAD
```

`kakapo --help`에 전체 플래그가 있습니다. `--base`는 어떤 revision이든 받고 실행 시점에 검증하며, `--staged`와는 함께 쓸 수 없습니다. 드롭다운보다 더 좁게 잘라 보고 싶다면, 툴바 아래 patch set 바가 브랜치의 커밋 하나와 다른 하나를 직접 비교하고, `⌘9`로 커밋 그래프를 열어 Enter를 누르면 그 커밋이 메인 리뷰에서 열립니다.

### base가 발밑에서 움직였을 때

브랜치가 갈라진 뒤 base에 커밋이 올라왔다면, 영향받은 행에 변경 목록이 그걸 표시합니다:

| 배지 | |
| --- | --- |
| **충돌** | base가 **같은 줄**을 바꿨습니다. 깨끗하게 병합되지 않습니다. |
| **갈라짐** | base가 이 파일의 **다른 곳**을 바꿨습니다. 병합은 되지만, 지금 보고 있는 게 전부는 아닙니다. |

양쪽을 **갈라진 커밋 기준**으로 비교하므로 줄 번호가 서로 맞습니다. 로컬 오브젝트 DB만 읽습니다 — fetch도, 계정도 없고, 아무것도 쓰지 않습니다(워킹트리·인덱스·ref 전부). **커밋 안 된 변경에도 동작**하는데, 에이전트가 방금 쓴 작업이 보통 그 상태입니다. base가 움직이지 않았다면 `git merge-base` 한 번으로 끝납니다.

## 돌아다니기

대부분은 원래부터 IntelliJ 키맵이었습니다: `⌘B` 사용처, `⌥F7` 사용처 찾기, `⌘⌥B` 구현, `⌘⌥O`
워크스페이스 심볼, `⌘E` 최근
파일, `⌘⇧F` 전체 검색, `⌘L` 줄 이동, `⌥F1` 사이드바에서 보기, `F2`·`⇧F2` 다음 문제, `⌘[`·`⌘]` 뒤로·앞으로,
`⌘↓` 또는 `⌘`+클릭으로 정의로.

이번에 더한 것:

**사용처 찾기** (`⌥F7`) — `⌘B`가 주는 답을, 각 사용처가 *무엇인지*로 묶어서 보여 줍니다. import끼리,
쓰기끼리, `extends` 절, `new`, 타입 파라미터, 그리고 주석·문자열에서 이름만 언급한 줄끼리. 한 심볼의 참조
40곳은 스크롤하는 목록이지만, 같은 40곳을 여덟 개 머리글 아래 놓으면 읽는 목록이 됩니다 — 그리고 "이 중
어디가 값을 쓰는가"가 보통 그 키를 누른 이유입니다. 묶음 이름은 IntelliJ의 것 그대로입니다("값 쓰기",
"extends·implements 절에서 사용", "인스턴스 생성"). 여기서 지어낸 게 아니라 intellij-community의
`UsageViewBundle.properties`에서 가져왔으니, IDE를 아는 사람이 보던 이름을 그대로 봅니다. 평범한 호출에는
IntelliJ에도 사용 유형이 없고, *분류되지 않음*으로 묶입니다.

주석·문자열 사용처는 **버리지 않고** *코드가 아닌 사용처* 구분선 아래에 둡니다. 이건 달라진 점입니다:
커서 팝업은 그것들을 조용히 버렸고, 주석에 네 번 언급된 이름에 "사용처 없음"은 틀린 답입니다. `⌥P`는 —
전체 검색과 같은 키, 같은 토글 — 그것들과 테스트 파일을 다시 걸러냅니다. 줄 하나로는 어떤 선언이 필드인지
지역 변수인지 알 수 없으므로, IntelliJ의 그 두 유형은 표에 넣지 않았습니다: 절반만 맞는 머리글은 머리글이
없는 것보다 나쁩니다.

**이 파일에서 강조** (`⌘F7` · `⌘⇧F7`) — 열린 파일에서 커서 아래 심볼이 나오는 모든 자리, 쓰기는 다른
색으로, `⌘⌥↓`·`⌘⌥↑`로 밟고, `Esc`로 치웁니다. IntelliJ의 Find Usages in File과 Highlight Usages in
File이 같은 일을 두 코드로 하는 것입니다. 이쪽은 의미 기반이 아니라 **이름 기반**이어서 — 이름이 같은 두
지역 변수가 함께 켜집니다, IntelliJ의 Find Word at Caret이 그렇듯 — language server에 묻지 않고, 차가운
서버가 아직 인덱싱 중일 때도 답합니다. 그 차이가 중요할 때는 `⌥F7`이 의미 기반 답입니다. 이 코드들은
전에는 `F8`·`⇧F8` 코멘트 이동의 두 번째 표기였습니다. 중복 하나가 IntelliJ의 파일 내 사용처 키 두 개보다
값지지는 않습니다.

**모듈, 그리고 어느 파일이 테스트인지** — IntelliJ는 결과를 평평하게 보여 주지 않습니다. 모든 목록이
파일이 *무엇인지*로 나뉩니다: 어느 모듈에 속하는지, 그리고 프로덕션 코드인지 테스트 코드인지
라이브러리인지. 카카포도 이제 그 구분을 프로젝트에서 직접 읽습니다 — IntelliJ로 한 번 열어 본
저장소라면 `.idea/modules.xml`과 `.iml` 파일(`isTestSource="true"`가 IDE 자신의 답이 있는 자리),
없으면 빌드 도구의 워크스페이스 선언: pnpm, npm workspaces, Cargo 워크스페이스, `go.work`,
`settings.gradle`, Maven 집합 pom. 그 어느 것도 없을 때만 경로 이름으로 추측합니다.

그래서 경로가 나열되는 자리마다: 파일 트리와 변경 트리는 테스트 파일에 색을 주고 모듈 루트인
디렉터리에 모듈 이름을 붙입니다. 파일로 이동·심볼로 이동·문제 목록은 각 줄 오른쪽에 모듈을
적습니다 — "어느 `Button.ts`?"라는 질문이 실제로 갈리는 지점이 그것입니다. 그리고 사용처 뷰(`⌥F7`)는
IntelliJ의 묶음 규칙 전부를 갖게 됩니다.

**사용처 뷰의 두 툴바** — IntelliJ의 사용처 뷰는 트리이고, 그 트리는 순위가 붙은 묶음 규칙의 겹입니다:
코드가 아닌 것, 프로덕션·테스트, 사용 종류, 모듈, 디렉터리, 파일 (intellij-community의
`UsageGroupingRulesDefaultRanks` — 그 순서가 취향 문제가 아닌 이유가 이 순위입니다). 각 순위가 목록
위의 칩 하나이고, 기본값도 IntelliJ 그대로입니다: 사용 종류·모듈·파일은 켜짐, 모듈 계층은 펴진 상태,
프로덕션·테스트는 직접 켤 때까지 꺼짐. 그 옆은 거르기 툴바 — 값 읽기·값 쓰기·import 보이기 — 와 원래
있던 `⌥P`입니다. 단축키도 IntelliJ의 `$default.xml`에서 왔습니다: `⌃⌥T`·`⌃⌥M`·`⌃⌥P`·`⌃⌥F`가 여기서는
`⌘⌥T`·`⌘⌥M`·`⌘⌥P`·`⌘⌥F`로 옵니다. 나누어도 나뉘지 않을 구분은 그리지 않습니다: 모듈이 하나인
저장소에는 모듈 머리글이 없고, 전부 호출 자리인 목록에는 머리글이 아예 없습니다.

**보이는 모습** — IntelliJ는 "테스트 파일"이라고 글자로 말하지 않습니다. 행에 색을 칠하고(File Colors:
테스트는 초록, 생성된 코드는 노랑 — `FileColorManagerImpl`의 값 그대로) 폴더 아이콘에 표시를 답니다.
카카포도 이제 두 트리와 편집기 탭에서 그렇게 하고, 테스트 소스 루트에는 `testSourceFolder` 아이콘의
초록·주황 화살표를, 모듈 루트에는 `Module` 아이콘의 파란 사각형을, 라이브러리에는 그 막대를 답니다 —
폴리곤과 색값은 IntelliJ 것이고, 그 위에 얹히는 폴더 윤곽만 카카포 것입니다. 사용처 뷰는 트리입니다:
모든 노드가 접히고, 자기가 무엇인지에 맞는 아이콘을 달고, 아래에 몇 곳이 있는지를 말합니다. 해당
심볼은 그 줄 안에서 굵게 표시되고, 모두 펼치기·접기는 IntelliJ 사용처 뷰 툴바에 있는 그 두 버튼입니다.
파일 **이름** 색은 건드리지 않았습니다 — 여기서 그 색은 이미 새 파일·수정·스테이지를 뜻하고, 같은
픽셀에 뜻을 하나 더 얹으면 읽는 사람이 둘 중 무엇인지 알 수 없게 됩니다.

**전체 검색의 범위** (`⌥S`) — IntelliJ의 범위 선택을, 리뷰에서 의미가 있는 것들로: 프로젝트 전체,
프로덕션 파일, 테스트 파일, 이 파일의 모듈, 또는 이 변경이 건드린 파일만. 범위는 답을 걸러내는 게
아니라 질문과 *함께* 갑니다 — ripgrep에게는 최대 500건만 물어보니, 나중에 거르면 엉뚱한 500건을 먼저
잘라낸 뒤가 됩니다.

**전체 검색의 세 가지 보조 키** (`⌥M` 대소문자 구분, `⌥W` 단어 단위, `⌥X` 정규식) — IntelliJ의 `Cc`,
`W`, `.*`이고 각각 ripgrep 플래그 하나입니다. 확장자는 `⌥E`, 주석·테스트 제외는 `⌥P`로 전과 같습니다. 셋
다 꺼져 있으면 검색은 원래대로 smart-case(소문자 질의는 대소문자를 무시하고, 대문자가 섞인 질의는 구분)와
문자열 그대로입니다. 컴파일되지 않는 식은 검색하지 않고 잘못된 식이라고 말합니다 — 정규식 오타에 "결과
없음"은 리뷰어가 믿어 버릴 틀린 답입니다. ripgrep에게 물을 수 없는 단독 HTML 리뷰도 같은 세 가지를
페이지 안에서 적용합니다.

**이 파일의 구조** (`⌘F12`) — 열린 파일의 모든 심볼을 중첩만큼 들여써서 보여 주고, 타이핑으로 걸러냅니다
(IntelliJ처럼 **이름만** 맞춥니다. 한글 자판을 켠 채로 친 질의는 그 키들로 되읽습니다). `Enter`는 심볼의
이름 위로 갑니다. language server가 답하고, 그 언어에 서버가 없으면 Find Usages를 받치는 선언 인덱스가
답하며 — 휴리스틱이라고 표시합니다.

**심볼 단위 이동** (`⌥↓` · `⌥↑`) — 다음·이전 심볼 경계. IntelliJ의 next/previous method입니다. `⌃↓`·`⌃↑`가
아닌 이유: kakapo의 단축키 표는 Command와 Control을 같은 기호로 적고(한 표로 두 플랫폼), `⌘↓`는 이미
정의로 가기입니다.

**타입 선언으로** (`⌘⇧B`) — 커서 아래 대상 자체가 아니라, 그 **타입**이 선언된 곳.

**최근 위치** (`⌘⇧E`) — 뒤로·앞으로 이력을 `⌘[`로 한 칸씩 밟는 대신 목록으로. 최신순이고, 지금 있는 자리를
표시합니다. `Enter`는 diff의 어느 쪽이었는지까지 포함해 위치를 복원합니다.

**파일 검색** (`⌘P`) — 이름으로, `store.ts:42`처럼 줄까지. `⇧⌘O`가 아닌 이유는 여기서 그게 새 창으로
폴더 열기이고, 데스크톱 앱의 관례는 지킬 만하기 때문입니다.

**두 가지 계층** (`⌘⌥H` 호출, `⌘⇧H` 타입) — 한 단계씩 펼치는 트리입니다. "누가 이걸 호출하나"는 질문의
절반이고, 나머지 절반은 "그럼 그걸 누가 호출하나"이기 때문입니다. `⇢`로 펼치고 `⇠`로 접고, 같은 코드를 다시
누르면 방향이 바뀝니다 (IntelliJ의 두 탭을 한 키로). IntelliJ의 `⌃`가 아니라 `⌘`인 이유는 위와 같습니다.
language server에 계층 요청이 없으면, 관계가 선언 줄에 적히는 언어들(`class Child extends Base`,
`class Worker(Base):`)에 대해 선언 텍스트 휴리스틱이 답합니다. 아무것도 답할 수 없으면 패널이 **이유**를
말합니다 — "아무도 호출하지 않는다"처럼 보이지 않게.

**상위로** (`⌘U`), **이 파일의 테스트로** (`⌘⇧T`) — 두 번째는 내장 언어들이 쓰는 이름 관례(`.test.`·
`.spec.`, `_test`, `test_`, `Test` 접미사)로 양방향이며, 가까운 디렉터리가 이깁니다. `thing.test.ts`가
스무 개인 모노레포에서도 이 파일의 것이 열립니다.

**북마크** (`F3`, `⌘F3`) — 할 말은 없고 다시 오고 싶은 자리. 할 말이 **있으면** 그건 코멘트이고, kakapo는
그걸 이미 코드 옆에 둡니다. 번호(니모닉) 북마크도 있습니다: `⇧⌥3`은 이 줄에 3번을 주고, `⌥3`은 어디서든
그 줄로 돌아옵니다. 한 번호는 한 줄에만 붙습니다. IntelliJ의 `⌃`가 아니라 `⌥`인 이유는 `⌘1`·`⌘0`·`⌘9`가
이미 Files 패널·Changes 패널·이력이기 때문입니다. 북마크는 kakapo의 워크스페이스 상태에 있고, 저장소에는
쓰지 않습니다.

**액션 찾기** (`⌘⇧A`) — 이 앱이 실행할 수 있는 모든 명령을 이름으로, 단축키와 함께. 거의 공짜인 이유는
명령이 이미 **데이터**이기 때문입니다: [src/shortcuts.ts](src/shortcuts.ts)는 설정 시트가 그리고,
`data-keyhint`가 채워지고, 디스패처가 id로 핸들러를 붙이는 하나의 표입니다. 그러니 목록은 그 표를 검색하는
것이고, 실행은 키를 눌렀을 때와 같은 호출입니다. 단축키를 쳐서 그 액션을 찾을 수도 있습니다 — 이 목록을
여는 이유의 나머지 절반입니다. 페이지가 실제로 부를 수 있는 것만 올립니다: `⌘O`는 OS 메뉴를 통해 폴더를
열고, 여기서는 부를 수 없습니다.

**빠른 정의** (`⌥Space`, `⌘Y`) — 정의의 코드를 커서 옆 상자에, 아무 데도 가지 않고. `⌘↓`는 거기로 가고
싶을 때이고, 이건 다른 걸 읽던 중에 "이 호출이 뭘 하지"일 때입니다. 리뷰 바깥의 정의는 빈 상자 대신 어디에
있는지 말합니다.

**코드 분석** (`F1`, `⌘⇧P`, `⌘F1`, `⌘6`) — 여기 language server들은 이미 여덟 가지를 답하고 있었는데,
전부 *어디에 있나*였습니다. `textDocument/hover`가 아홉 번째이자 *무엇인가*를 답하는 유일한 요청입니다.
`F1`은 그 답을 통째로 보여 주고(Markdown이고, 소스 미리보기와 같은 렌더러를 지납니다), `⌘⇧P`는 그중
시그니처 한 줄만 꺼냅니다. `⌘F1`은 커서가 있는 줄의 문제를 읽어 줍니다 — 지금까지는 마우스로만 닿는
툴팁이었습니다.

`⌘6`은 Problems 뷰입니다. 열린 파일만이 아니라 **리뷰 전체**의 에러·경고를, 몇 파일씩 물어서 답이
도착하는 대로 채웁니다. 에러가 경고 위로 정렬되고, `⌥E`는 경고를 숨기며, language server가 없는 파일은
조용히 0건으로 묻히지 않고 **세어서 말합니다** — 절반을 확인하지도 못한 리뷰에 "문제 없음"은 이 목록이
낼 수 있는 유일한 틀린 답이기 때문입니다. 인스펙션과 데이터플로 슬라이싱은 여기 없고, 있을 수도 없습니다:
컴파일러의 프로그램 모델이 필요합니다. 이 앱의 인스펙션은 실제 language server들의 진단입니다.

**옮기지 않은 것과 그 이유.** *Show File Path* (`⌃⌥F12`): 소스 뷰 위 breadcrumb가 이미 항상 보여 주고,
`⌥F1`이 사이드바에서 찾아 줍니다. *Structure 도구 창*: `⌘F12` 팝업이 그중 읽는 쪽이고, 고정 패널은
작업공간 가구입니다. *Inspect Code*·*Code Cleanup*·*Analyze ▸ Data Flow*: 셋 다 컴파일러의 모델 위에서
도는 IntelliJ 자체 엔진이 필요합니다 — 이 앱이 대신 가진 것은 프로젝트의 진짜 language server 진단이고,
`⌘6`이 그걸 모읍니다. *Find Usages Settings*와 *Structural Search*: 둘 다 이 앱에 모델이 없는 검색 범위와
패턴에 관한 것입니다. *라이브 템플릿*과 그 파라미터 이동: 여기에는 입력할 것이 없습니다.

**전체 검색** (`⇧⇧`) — 모든 섹션이 옆에 붙은 런처. 두 번 누르기는 [src/shortcuts.ts](src/shortcuts.ts)의
그 표에 코드로 적혀 있고 하나의 매처가 인식합니다 — 재지정도 되고, 코드가 적힌 두 번째 장소도 없습니다.

**이식하지 않은 것.** Go to Related Symbol은 IntelliJ에서 프레임워크별 기능입니다 (템플릿과 그 컨트롤러,
빈과 그 XML). `⌘⇧T`가 그중 어느 프로젝트에서나 일반화되는 부분입니다. 그리고 `⌘↑`는 IntelliJ의 breadcrumb
팝업이 아니라 **지금 보는 파일 위치로 사이드바를 여는** 동작입니다 — kakapo의 내비게이션 바는 사이드바이고,
두 번째 표면을 만드는 대신 같은 동작으로 둡니다.

## Diff 읽기

Diff는 좌우 두 쪽으로 보여 주고, 바뀐 줄 안에서 **실제로 달라진 글자**를 따로 표시합니다. 그리고 창
오른쪽 끝에는 열려 있는 파일의 변경 전체를 한눈에 보여 주는 눈금이 있습니다 — 어디에 있고, 파일의 얼마를
차지하고, 내 코멘트가 어디 붙었고, 지금 내가 그중 어디를 보고 있는지. 눈금을 클릭하면 그 자리로 갑니다.

읽는 방식 세 가지를 바꿀 수 있고, 그중 둘은 `git diff`를 다시 돕니다:

| 어디서 | 무엇을 |
| --- | --- |
| Diff 메뉴 | **공백**: 모든 차이를 차이로 보기 / 공백의 양만 무시(`-b`) / 아예 무시(`-w`). `⌘⇧W`가 셋을 순환합니다. |
| Diff 메뉴 | **변경 주변에 유지할 안 바뀐 줄 수**: 3, 12(기본), 50, 또는 파일 전체. |
| 설정 | **바뀐 줄**: 달라진 글자만 / 줄 전체 / 거터만 색칠. |

앞의 둘은 창 단위입니다 — 같은 저장소를 두 창에서 서로 다른 규칙으로 읽을 수 있습니다. 세 번째는 항상
들어 있는 마크업을 어떻게 읽을지의 문제라, 고르는 순간 적용됩니다.

**IntelliJ diff에서 이식하지 않은 것:** 단일 열(unified) 보기와 공백을 글리프로 그리는 기능. unified
보기는 kakapo diff의 설정이 아니라 **두 번째 형태**입니다 — 캐럿 모델·행 정렬·코멘트 앵커·거터 레이어가
모두 2열 마크업을 읽습니다. 즉 옵션 하나가 아니라 리뷰 화면 자체를 바꾸는 일이고, 같은 hunk를 다르게
보는 방법 하나를 위해 그 바닥을 흔들 만한 가치는 없다고 판단했습니다.

## HTTP 요청 (`.http` 파일)

저장소의 `.http`·`.rest` 파일은 읽는 자리에서 그대로 실행됩니다. 요청마다 거터에 `▶`가 붙고 (소스 뷰와
diff 양쪽 모두), 응답은 그 요청 아래에 펼쳐집니다. 포맷은 JetBrains HTTP Client 그대로이므로, 같은 파일을
고치지 않고 kakapo와 IntelliJ에서 함께 씁니다.

```http
@base = https://api.example.com

### 로그인
# @name login
POST {{base}}/sessions
Content-Type: application/json

{ "user": "ada", "password": "{{$dotenv.PASSWORD}}" }

> {%
  client.global.set("token", response.body.token);
  client.test("토큰이 왔다", function () {
    client.assert(response.body.token, "응답에 토큰이 없음");
  });
%}

### 그 토큰으로 여는 프로필
# @timeout 5
GET {{base}}/me
Authorization: Bearer {{token}}

>> out/me.json
```

**요청.** `###`가 요청을 나누고 이름을 줍니다 (`# @name`도 되고, 이름 없는 요청은 `#1`). URL만 적으면
`GET`입니다. URL 뒤의 HTTP 버전은 URL에 포함되지 않습니다. 긴 URL은 `/`·`?`·`&`로 시작하는 들여쓴 줄로
나눌 수 있습니다. `GRAPHQL`은 `{query, variables}`로 POST합니다 — 오퍼레이션, 빈 줄, 그리고 변수 JSON.

**지시자** — 요청 위의 주석 줄에 씁니다: `@no-redirect`, `@no-cookie-jar`, `@no-log`,
`@no-auto-encoding`, `@timeout 600`, `@connection-timeout 2 m` (`ms`·`s`·`m`, 기본은 초). 두 타임아웃은
둘 중 **큰 쪽**으로 하나의 기한이 됩니다 — 연결과 읽기 사이에 끼어들 지점이 없어 따로 적용할 수 없고,
요청한 어느 쪽보다 짧은 기한은 틀린 답이기 때문입니다.

**바디.** 인라인으로 쓰거나, `< ./body.bin`으로 파일의 바이트를 그대로 보내거나, `<@ ./body.json`으로
파일 안의 `{{변수}}`를 먼저 치환해 보냅니다. `multipart/form-data`는 `--boundary` 블록에서 파트를
조립합니다. `filename=`이 있는 파트는 그 파일의 바이트로, 없는 파트는 파일 내용을 그 필드의 텍스트로
보냅니다.

**변수.** 파일 안의 `@name = value`, `http-client.env.json`과 `http-client.private.env.json` (저장소
루트뿐 아니라 요청 파일 옆에서도 찾고, 가까운 파일이 이깁니다), 모든 환경이 올라앉는 `$shared` 섹션,
`.env`에서 읽는 `{{$dotenv.NAME}}`, 프로세스 환경변수 `{{$env.NAME}}`, 그리고 JSON을 담은 변수로 들어가는
점 표기 (`{{client.host.url}}`). 동적 변수: `$uuid`, `$timestamp`, `$isoTimestamp`, `$randomInt`,
`$random.integer/float/alphabetic/alphanumeric/hexadecimal/email/uuid`, `$projectRoot`, `$historyFolder`.
이름 붙은 응답도 읽습니다 — `{{login.response.body.$.token}}`, `.headers.Location`, `.status`. 값이 없는
`{{name}}`은 요청을 보내지 않고 **어느 이름인지** 말해 줍니다. 그대로 보내서 scheme 오류를 받는 것보다
원인에 가깝습니다.

**스크립트.** 요청 앞의 `< {% … %}`, 뒤의 `> {% … %}` 또는 `> ./handler.js`. IntelliJ API 그대로:
`client.global`, `client.test`, `client.assert`, `client.log`, `client.exit`,
`response.status/body/contentType/headers`, `request.body/url/headers/method/variables/environment`,
`jsonPath`, `xpath`, `crypto.sha1/sha256/md5`과 `crypto.hmac.*`, `await sleep(ms)`, 그리고 동적 변수를
그냥 식별자로. 테스트 결과와 `client.log` 출력은 응답과 함께 보여 줍니다 — 단언하고 통과한 핸들러는
통과했다고 **말해야** 합니다.

스크립트는 리뷰 창에서 돕니다. Electron이 그 창을 sandbox + contextIsolation으로, node 통합 없이 띄우므로
핸들러에는 `require`도 `fs`도 `process`도 없습니다. 그리고 눈앞에 텍스트가 보이는 요청에 `▶`를 누르기
전까지 아무것도 실행되지 않습니다. 저장소를 읽는 일이 그 저장소를 실행하는 일이 되어서는 안 됩니다.

**저장.** `>> out.json`은 기존 파일 옆에 (`out-1.json`), `>>! out.json`은 덮어씁니다.
`{{$historyFolder}}`는 kakapo 자신의 app-data 미러로 풀립니다 — 읽고 있는 저장소에 kakapo의 상태를 쓰지
않습니다. 쿠키 잼도 거기 있고, IntelliJ와 같은 `# domain path name value date` 형식이라 그대로 읽힙니다.

**다른 파일 실행.** `run ./smoke.http`는 그 파일의 모든 요청을, `run #login`은 이름으로 하나를 (이 파일
먼저, 그다음 `import`한 파일들에서) 실행합니다. `run ./other.http#login (@host = https://staging.test)`은
그 호출에만 변수를 덮어씁니다. 자기 자신을 실행하려는 파일은 멈추고 그렇다고 말합니다.

**컬렉션.** 변수 값이 JSON 배열이면 요청이 반복문이 됩니다: `@ids = [1, 2, 3]`에 
`GET {{base}}/items/{{ids}}`면 요청 세 개가 나가고, 핸들러는 `request.iteration()`으로 자기가 몇 번째인지
압니다.

**스크립트 모듈.** 핸들러는 옆의 `.js` 파일에서 `import`할 수 있습니다 (named·default·namespace·이름
바꾸기 전부). 모듈끼리의 import도 됩니다. 핸들러와 **같은 샌드박스**에서 돕니다 — `require`도 `fs`도
`process`도 없습니다.

**클라이언트 인증서.** `http-client.private.env.json`의 `SSLConfiguration` (`clientCertificate`,
`clientCertificateKey`, `verifyHostCertificate`)을 따릅니다. 인증서는 main 프로세스가 리뷰 안에서 읽고,
페이지를 거치지 않습니다. 암호가 걸린 키는 이름을 들어 거절합니다 — IntelliJ는 대화형으로 묻지만 kakapo는
물을 자리가 없습니다.

**이식하지 않은 것.** gRPC (protobuf 런타임이 필요한데, 이 CLI는 리뷰상의 이유 없는 런타임 의존성을 지지
않습니다), OAuth2 `Security.Auth` 플로우, `@use-os-credentials` (지시자로는 인식하지만 넘길 OS 자격증명
저장소가 없습니다), `$exampleServer`, Java Faker 생성기 전체 (흔한 것들은 있고, 없는 것은 이름을 들어
알려 줍니다), 그리고 `curl` 명령 **가져오기** — kakapo는 읽고 있는 파일에 쓰지 않으므로 넣을 자리가
없습니다. WebSocket은 파일에 적힌 메시지를 보내고 교환을 보여 줍니다 — IntelliJ의 실시간 콘솔은
아닙니다.

## Git 이력

`⌘9`는 저장소의 읽기 전용 이력들을 엽니다. 여기서 무엇도 바뀌지 않습니다 — 커밋·push·rebase·checkout·
스태시 적용이 없습니다. kakapo가 하는 일은 누군가(혹은 무언가)가 이미 만든 변경을 **읽는** 것입니다.

**세 가지 종류** — 바에서 전환합니다: **커밋** (브랜치 레인과 ref 칩이 있는 그래프 로그), **Reflog**
(`HEAD`가 지나온 자리 — reset이나 rebase가 떨어뜨린 커밋을 아직 쥐고 있는 유일한 화면), **스태시**.
어느 쪽이든 한 줄을 열면 평소의 리뷰 화면에서 열립니다. diff·네비게이션·코멘트가 그대로 따라옵니다.
스태시는 자신의 첫 부모, 즉 스태시를 만들 때 `HEAD`가 있던 자리를 기준으로 열립니다.

**필터는 git이 적용합니다.** 이미 그려진 줄을 숨기는 게 아닙니다: 작성자, 경로, 전체 대신 걸어갈
브랜치·태그·리비전, 변경된 코드(git의 pickaxe), 날짜 범위, 메시지, 그리고 전체 브랜치 대 현재 브랜치. 이 구분이 중요합니다 — 한 페이지는 수백
개의 커밋이므로, 그 안에서 걸러내는 방식은 "Ada의 커밋이 없다"고 답하면서 실제로는 "최근 수백 개 중에
없다"를 뜻합니다.

**커밋으로 이동.** 검색창에 해시·브랜치·태그·`HEAD~3`을 치면, 그것이 커밋을 가리키는 경우 현재 페이지에
없어도 열어 주겠다고 띠가 제안합니다. 아무것도 가리키지 않는 말은 그냥 메시지 필터로 남습니다. `⌘C`는
선택한 커밋의 해시를 복사합니다.

**파일 하나, 줄 하나.** 사이드바에서 파일에 `⌥Enter` → 그 파일의 이력을, 이름이 바뀐 지점을 넘어서
따라갑니다. 줄 번호를 오른쪽 클릭하면 거터에 blame이 펼쳐지고 (날짜·작성자, 나이에 따라 색이 들어갑니다),
한 줄의 귀속을 클릭하면 그 줄을 쓴 커밋이 열립니다. 이력이 열린 상태에서 줄 번호를 오른쪽 클릭하면 그 한
줄로 목록이 좁혀집니다 (`git log -L`) — 그 줄을 실제로 바꾼 커밋만 보입니다.

**두 커밋 비교.** Shift+클릭(또는 `⇧↑↓`)으로 두 줄을 고르고 범위를 열면, 그 두 패치 세트 사이의 모든
변경이 하나의 리뷰로 열립니다. `⌥A` / `⌥U` / `⌥C`는 같은 질문의 브랜치 단위 버전입니다.

## 내장 language server

| 언어 | 분석기 | 함께 들어 있는 실행 환경 |
| --- | --- | --- |
| TypeScript / JavaScript | `typescript-language-server` | Electron의 Node 호스트 |
| Python | Pyright | Electron의 Node 호스트 |
| Go | `gopls` | Go SDK |
| Rust | `rust-analyzer` | Cargo, Rust stable, `rust-src` |
| C / C++ | `clangd` | 플랫폼 네이티브 clangd |
| Java | Eclipse JDT LS | Temurin JRE 21 |
| Kotlin | JetBrains Kotlin LSP | 전용 JetBrains Runtime |
| Ruby | Sorbet | 플랫폼 네이티브 Sorbet |
| PHP | Phpactor | 정적 PHP 8.4 런타임 |

배포본은 항상 자기 번들을 우선하며 셸의 `PATH`는 뒤지지 않습니다. 명시한 `KAKAPO_LSP_<LANGUAGE>` 실행 파일만 이를 덮어쓸 수 있습니다. 읽고 있는 저장소 안의 실행 파일은 `KAKAPO_LSP_PROJECT_SERVERS=1`을 설정하지 않는 한 후보가 **아닙니다** — 저장소를 읽는 일이 그 저장소의 코드를 실행하는 일이 되어서는 안 되고, 분석 예열은 묻지 않고 서버를 띄웁니다. 패키징은 9개 번들의 존재와 실제 cross-file definition을 모두 확인한 뒤에만 진행됩니다. 지원 밖 언어이거나 서버가 답하지 못하면, 출처가 표시된 정규식 인덱스로 폴백합니다.

의미 분석의 품질은 프로젝트 메타데이터에도 달려 있습니다 — Java/Kotlin은 Maven·Gradle 모델, Rust는 `Cargo.toml`, Go는 `go.mod`, 큰 C/C++ 프로젝트는 `compile_commands.json`, PHP는 Composer autoload. 분석 캐시와 JDT/Kotlin workspace는 저장소 안이 아니라 임시·앱 데이터 영역에 둡니다.

## 상태가 저장되는 곳

리뷰 스레드는 저장소의 git 디렉터리 안에 있습니다.

```text
.git/worktrees/<name>/kakapo/comments.jsonl   # 이 worktree의 리뷰 대화
```

나머지는 워크스페이스 절대 경로별로 OS 앱 데이터 디렉터리에 미러링됩니다. macOS에서 `/Users/me/repos/acme/turtle`을 열었다면:

```text
~/Library/Application Support/Kakapo/workspaces/Users/me/repos/acme/turtle/
├── state.json
├── perf/
└── review/app-review.html
```

경로를 해시로 숨기지 않아 직접 열어볼 수 있고, 저장소 루트·내부 패키지·다른 worktree를 동시에 열어도 각각 독립된 상태를 가집니다.

## 개발

```bash
npm install
npm run lsp:install
npm run build
npm run lsp:smoke
npm test
npm run smoke
```

`npm run mermaid:smoke`는 의도적으로 분리되어 있습니다. Mermaid의 `render()`는 `getBBox`로 텍스트를
측정하는데 jsdom에 그 API가 없어서, 다이어그램이 실제로 배치되는지는 진짜 앱에서만 답할 수 있습니다.
20초쯤 창이 떴다 사라지며, 이 체크아웃에서 띄운 Kakapo가 실행 중이면 안 됩니다.

로컬 빌드로 다른 저장소를 검토:

```bash
npm run dev -- --cwd /path/to/repository
```

앱과 설치용 디스크 이미지 빌드:

```bash
npm run dist:mac:dmg
```

language server를 번들하고, 빌드하고, Apple Silicon 앱을 패키징한 뒤 번들 서버 스모크 테스트를 돌려 `release/Kakapo-<version>-arm64.dmg`를 만듭니다. kakapo는 Apple Silicon macOS로만 패키징됩니다.

성능은 `npm run benchmark`(`-- --files 5000 --changed 200 --lines 120`으로 더 큰 합성 저장소)로 측정합니다.

테스트는 실제 임시 Git 저장소와 빌드된 `dist/`를 사용해 diff, 검색, 코멘트, 히스토리, LSP 폴백, 상태 영속화, Electron 레이아웃을 회귀 검증합니다. 사용자 흐름 목록은 [test/USER_FLOWS.md](test/USER_FLOWS.md)에 있습니다. 스위트가 닿지 못하는 두 가지는 따로 있습니다: `npm run mermaid:smoke`와 `npm run nav:smoke`는 실제 앱을 띄워 Chrome DevTools Protocol로 조작합니다 — 진짜 키 이벤트, 진짜 language server, 그리고 실제로 그려진 것에 대한 `getComputedStyle`. 중첩이 없는 구조 목록(tsserver는 평평한 심볼 형태로 답합니다)과 아무것도 안 그려지던 북마크 표시(의사 요소의 `attr()`은 행이 아니라 셀의 속성을 읽습니다)가 거기서 잡혔고, 둘 다 jsdom에는 보이지 않습니다. `KAKAPO_SMOKE_SHOTS=<디렉터리>`를 주면 스크린샷이 남습니다.

## 설계 원칙

- 채팅 요약보다 실제 diff를 신뢰합니다.
- 확정된 영향과 확인이 필요한 후보를 구분합니다.
- 리뷰 근거는 파일과 라인 곁에 둡니다.
- 상태는 로컬에 평문 Markdown/JSON/JSONL로 남깁니다.
- 특정 AI, 에디터 플러그인, worktree 전략, 호스팅 서비스에 종속되지 않습니다.
